# 手机端访问 dsh 指南（Tailscale）

> 本文件是真实踩坑记录总结。用它指导其他用户时，把下面标注「本机」的具体值换成对方机器的值即可。
> 默认假设：用户只在电脑上跑一个 dsh（标准端口 **3080**）。「多实例」部分（3081 等）是作者本人机器的特例，普通用户跳过即可，那里面的教训是通用的：**端口全链路一致**。

## TL;DR

dsh 出于安全**只监听 127.0.0.1**，且新版 dsh（本机实测：喵版开发版）**硬性禁止 `--host 0.0.0.0`**。手机远程访问的正确姿势只有一条路：

**保持 dsh 本机监听 → 用 Tailscale Serve 做反向代理 → 启动时用 `--trusted-host` 放行 Tailscale 地址。**

另外 iOS 上访问 `http://<Tailscale-IP>:端口` 会踩「本地网络权限」的坑（页面能开、聊天记录出不来），**推荐手机直接用 HTTPS 域名入口**（`https://<MagicDNS域名>`，格式 `<机器名>.tail<编号>.ts.net`）。

## 原理

```
手机浏览器 ──Tailscale 网络──> 电脑 tailscaled (serve 代理)
                                   │ 转发
                                   v
                        dsh web 监听 127.0.0.1:3080
```

- dsh 的 `/api` 有一道「浏览器信任围栏」：按请求的 Host/Origin 校验，默认只信 `127.0.0.1`，白名单来自启动参数 `--trusted-host`。
- Tailscale Serve 的转发配置是**持久化**的，重启电脑不丢。
- 前置条件：电脑和手机都登录**同一个 Tailscale 账号**；手机装 Tailscale App 并保持连接；电脑端 Tailscale 常驻运行。

## 端口与多实例（通用教训）

默认情况：dsh 标准端口就是 **3080**，手机和电脑访问同一个服务，不需要考虑别的端口。

但如果用户像本机一样**同时跑多个 dsh 实例**（本机特例：额外装了喵版开发版，跑在 3081），记住一条核心教训：

> **每个实例的「监听端口 = serve 转发目标端口 = `--trusted-host` 白名单里的端口」，三者必须全链路一致；不同实例必须用不同端口。**

本机特例的端口表（仅供理解「多实例」概念，普通用户没有 3081）：

| 端口 | 版本 | 说明 |
|---|---|---|
| 3080 | npm 官方版 | 所有用户的默认情况，`start-dsh.bat` 启动 |
| 3081 | 喵版（本机特例） | 本机额外装的开发版，含插件，`start-meow.bat` 启动 |

## 八个坑（真实踩坑记录）

### 坑 1：手机输入 Tailscale IP 打不开网页

- **现象**：手机和电脑都登录了 Tailscale，手机访问 `http://<本机TS-IP>:3080` 打不开。
- **根因**：dsh 默认只监听 `127.0.0.1`，不监听 Tailscale 网卡，内核直接拒收。
- **错误尝试**：改 `--host 0.0.0.0`。新版 dsh（本机喵版实测）会直接拒绝启动：
  ```
  error: --host 0.0.0.0 is intentionally not supported yet for safety:
  it would expose remote code execution to the network
  ```
  这是硬编码安全设计，绕不过，也不要绕。即使某些旧版本支持，把 dsh 直接暴露到网络也有风险。
- **正解**：保持 `127.0.0.1` 监听，用 Tailscale Serve 转发（见下方「标准配置」）。这条对所有版本通用。

### 坑 2：`--trusted-host` 的端口必须与监听端口一致（多实例场景）

- **现象**：手机访问某个实例时 API 全部 403，另一个实例却正常。
- **根因**：该实例启动时 `--trusted-host` 配的端口和它实际监听的端口不一致。本机实踩案例：喵版实例监听 3081，白名单却配成了 `:3080`（旧方案遗留），结果手机访问 3081 全部 403。
- **解决**：**白名单端口跟着监听端口走**。监听 3080 就配 `--trusted-host <TS-IP>:3080`；监听 3081 就配 `--trusted-host <TS-IP>:3081`。每个实例各配各的，别照抄。

### 坑 3：开了 HTTPS 域名入口后 API 依然 403

- **现象**：HTTPS 入口通了、页面能开，但带 `Origin: https://<域名>` 的请求全部 403（不带 Origin 时是 200）。
- **根因**：信任围栏按 Origin 校验，白名单里只加了 IP，没加域名。
- **解决**：再追加一个域名形式的白名单：`--trusted-host <MagicDNS域名>`（域名不带端口）。最终启动参数同时包含 IP 白名单和域名白名单。

### 坑 4：iOS Safari 特有的 `Origin: null` 被硬拒

- **现象**：iOS Chrome 完全正常，Safari 看不了聊天记录、接口 403。
- **根因**：Safari 在无痕模式、从「添加到主屏幕」图标、书签、分享菜单或其它 App 跳转打开页面时，请求会带 `Origin: null`。dsh 的围栏**硬编码拒绝 null 来源**（防沙箱页面 CSRF），`--trusted-host null` 也无效——这是安全策略，不是配置问题。
- **解决**（浏览器端）：
  1. 关掉无痕模式；
  2. 在地址栏**直接输入** `https://<域名>` 回车打开；
  3. 删掉旧书签重新保存；
  4. 实在不行就用 Chrome（完全可用）。

### 坑 5：iOS 本地网络权限 —— 页面能开但「暂无会话」

- **现象**：`http://100.101.102.103:3080` 页面正常，聊天记录显示「暂无会话」。
- **根因**：`100.64.x.x` 是 iOS 认定的「本地网络」地址段（CGNAT 段）。iOS 14.5+ 会**静默拦截**发往该地址段的 WebSocket 长连接——页面和静态资源是普通请求不受影响，但聊天记录靠长连接推送，所以加载不出来。
- **解决**（二选一）：
  - 手机：设置 → 隐私与安全性 → 本地网络 → 打开对应浏览器的开关；
  - **推荐**：直接用 HTTPS 域名入口 `https://<域名>`，正式域名不触发本地网络限制，且加密更安全。

### 坑 6：HTTPS 入口报 `Serve is not enabled on your tailnet`

- **根因**：HTTPS（证书）功能需要 **Tailscale 账户管理员在控制台开启**，CLI 无权代开。
- **解决**：让用户本人点控制台授权链接（`https://login.tailscale.com/f/serve?node=<节点ID>`）或登录控制台开启 HTTPS，之后再配 serve。

### 坑 7：手机端 host.* 类操作永远 403 —— 这不是 bug

- **现象**：手机上触发某些操作时报 `transport failure for /api/host.pickDirectory: HTTP 403` 或 `/api/host.openPath: HTTP 403` 等。
- **根因**：`host.*` 接口族（选文件夹 `pickDirectory`、打开路径 `openPath` 等本机文件操作）是**本机专属接口**，dsh 设计上只允许 `Host=127.0.0.1` 的本地浏览器调用——因为这类操作等于让电脑弹授权、开文件夹，若允许远程触发，tailnet 内任何设备都能诱导电脑执行。实测验证：同一请求走域名入口（Origin 已在白名单）依然 403，而本机直连 127.0.0.1 是 200——白名单救不了它，这是硬编码设计。
- **正确用法**：涉及「选择/打开电脑文件夹」的操作一律在**电脑浏览器**上做；手机只用来浏览会话、对话、发消息。判断标准：报错路径里带 `/api/host.` 前缀的，都是本机专属，任何手机浏览器都无法也不应绕过。

### 坑 8：多个实例挤同一个端口（多实例场景）

- **现象**：同时跑两个 dsh 实例，第二个启动失败或端口冲突。
- **解决**：每个实例用独立端口（本机：官方版 3080、喵版 3081），各自启动脚本锁定自己的端口和 `--trusted-host`，互不干扰。

## 标准配置（默认：只有 3080）

### 启动脚本

以本机 `start-dsh.bat` 为例（已固化，重启服务自动带上）：

```
node dsh web --trusted-host %TSIP%:3080 --trusted-host <MagicDNS域名>
```

要点：`TSIP` 用 `tailscale ip -4` **动态获取**（TS IP 变化时不失效），失败回退写死的本机 IP；**不要**加 `--host`（保持 127.0.0.1 安全默认）。

### Tailscale Serve 转发

```
# TCP 转发（IP:端口 形式访问）
tailscale serve --bg --tcp 3080 tcp://127.0.0.1:3080

# HTTPS 域名入口（推荐手机使用；需先在控制台开启 HTTPS，端口语法以 `tailscale serve --help` 为准）
tailscale serve --bg https / http://127.0.0.1:3080
```

### 手机访问地址表

| 手机访问 | 到达 | 备注 |
|---|---|---|
| `http://<本机TS-IP>:3080` | dsh（3080） | iOS 需开「本地网络」权限 |
| `https://<域名>`（443） | dsh（3080） | **推荐**，无本地网络限制 |

本机具体值：TS-IP = `100.101.102.103`（示例占位，真实值用 `tailscale ip -4` 查，可能变化）；域名 = 本机的 **MagicDNS 域名**（Tailscale 官方叫法，格式 `<机器名>.tail<编号>.ts.net`，在 Tailscale 控制台 Machines 页的 DNS name 一列查看，`tailscale status` 或 `tailscale cert` 的提示里也能看到）。

## 多实例扩展（本机特例：额外跑了喵版 3081）

如果你也要跑第二个 dsh 实例（比如本机的喵版开发版），按「端口全链路一致」扩展：

**启动脚本**（本机 `start-meow.ps1`，注意 `--port 3081` 和 `:3081` 对应）：

```
pnpm dsh web --trusted-host ${tsip}:3081 --trusted-host <MagicDNS域名> --port 3081
```

**Serve 转发**（给第二个实例配独立的 TCP 端口和 HTTPS 端口）：

```
tailscale serve --bg --tcp 3081 tcp://127.0.0.1:3081
tailscale serve --bg https / http://127.0.0.1:3081    # 或指定独立端口如 8443
```

**手机访问追加**（与第一个实例并列）：

| 手机访问 | 到达 | 备注 |
|---|---|---|
| `http://<本机TS-IP>:3081` | 喵版（3081） | iOS 需开「本地网络」权限 |
| `https://<域名>:8443` | 喵版（3081） | 与 443 入口区分 |

双实例方案落地后，`tailscale serve status` 的输出大致长这样（具体值已用占位符替换）：

```
tcp://<TS-IP>:3081              → 127.0.0.1:3081
tcp://<MagicDNS域名>:3081        → 127.0.0.1:3081
https://<MagicDNS域名>            → 127.0.0.1:3080
https://<MagicDNS域名>:8443       → 127.0.0.1:3081
```

## 快速排障表

| 症状 | 原因 | 处理 |
|---|---|---|
| 偶发 HTTP 502（如 session.history） | 撞上 dsh 实例重启窗口，serve 网关拿不到上游响应 | 等几秒刷新即可；若无重启仍频发 502 才需查实例是否崩溃 |
| 完全打不开（连接失败/超时） | dsh 没跑 / serve 没配 / 电脑端 Tailscale 没开 | 电脑上 `netstat -ano \| findstr ":3080"`、`tailscale serve status` 排查 |
| 页面能开，接口 403 | 信任围栏缺白名单，或端口写错 | 核对 `--trusted-host`（IP:端口 + 域名都要加，端口与监听端口一致） |
| 多实例中某个实例 403、别的正常 | 该实例 trusted-host 端口配错 | 让该实例的白名单端口等于它自己的监听端口 |
| iOS 上「暂无会话」（http://IP 形式） | 本地网络权限拦截 WebSocket | 开「本地网络」权限，或改用 https 域名入口 |
| Safari 403 / Chrome 正常 | Safari 发了 `Origin: null` | 地址栏直接输入、关无痕、不用主屏幕图标和旧书签 |
| 添加工作区/打开文件夹 403（`/api/host.*`） | 设计如此，本机专属接口 | 在电脑浏览器上做这类操作 |
| HTTPS 配不了，报 not enabled | 控制台未开启 HTTPS | 账户管理员在 Tailscale 控制台授权 |

## 维护命令速查

```
tailscale serve status                      # 查看当前转发
tailscale serve --tcp=3080 off              # 关闭某条 TCP 转发
tailscale serve --https=443 off             # 关闭某条 HTTPS 转发
tailscale serve reset                       # 清空全部转发
tailscale ip -4                             # 查本机 Tailscale IP
```

serve 配置持久化，重启电脑不丢；但若换了机器、域名、Tailscale 账号，或增删 dsh 实例，需同步更新 serve 配置和启动脚本里的 `--trusted-host`（端口跟着监听端口走）。

### 平板/手机经 Tailscale 访问 DSH（必读：信任栅栏配置）

DSH Web 的 `/api` 有浏览器信任栅栏：Host 必须是回环地址，或命中启动时用 `--trusted-host` 声明的权威。经 Tailscale Serve 访问时 Host 是 MagicDNS 权威，**必须先把它加进信任名单，否则页面能打开但所有 /api 请求 403**（会话列表空白、插件数据加载失败）。

**一步配置**（以 MagicDNS 权威 `pc.xxx.ts.net` 为例，换成你自己的）：

```sh
# 启动 DSH 时追加 --trusted-host
dsh --profile web --host 127.0.0.1 --port 3080 --trusted-host pc.xxx.ts.net
```

**两条入口（二选一）**：

```sh
# A：不开压缩代理（默认），手机访问 https://pc.xxx.ts.net
tailscale serve --bg --https=443 http://127.0.0.1:3080

# B：经内置压缩代理（需在 patch 配置里开启 proxy.enabled），手机访问 https://pc.xxx.ts.net:8443
tailscale serve --bg --https=8443 http://127.0.0.1:8444
```

> 提示：
> - A 入口默认无端口后缀；B 入口 URL 需带 `:8443`。
> - Tailscale Serve 的 HTTPS 同时提供 `wss://` 升级与 PWA/Web Push 所需的安全上下文。
> - 若改用 Caddy / nginx 等反向代理，同样需要让 DSH 信任代理暴露的权威（`--trusted-host`）。
> - 局域网直连同理：把网关/反代对外权威加入 `--trusted-host`。
> - 安装时请保持插件原名 `meow-smooth`（改名安装会导致前端注册 id 不匹配，页面报「Failed to load plugins」）。

已验证环境：DSH 0.1.5-rc.1 · meow-smooth 0.7.1 · Tailscale 1.102.3（Windows PC + Android 手机）；DSH 0.1.1-rc.2 · meow-smooth 0.6.1 · Tailscale 1.102.3（Windows PC + Android 15 平板）。


## 桌面版专属（DeepSeek Harness 桌面 App）

> 前文全部假设 dsh 是「自己启动的服务」——有启动脚本、能加参数。桌面 App 不一样：
> **没有启动脚本，启动参数写死在程序里**，前文「改启动脚本加 `--trusted-host`」的正解对它一律失效。
> 以下为 0.1.7-rc.2 实测（2026-09-27）。

桌面 App（`DeepSeek Harness.exe`）内嵌了一个完整的 dsh web 服务，手机访问它就等于访问桌面版，数据同源：

| 项目 | 本机值 | 说明 |
|---|---|---|
| 内嵌 web 端口 | `127.0.0.1:19387` | **写死在桌面宿主**（dsh-desktop-host）里，不是随机端口；升级后用 netstat 复核 |
| 另一端口 3897 | 桌面宿主内部口 | 插件推送等内部用途，浏览器用不上 |
| 手机门 | `https://<MagicDNS域名>:19387` | serve 挂法同前文：`tailscale serve --bg --https=19387 http://127.0.0.1:19387` |

### 坑 9：token 抓不到——桌面版不打印 URL

- **现象**：`dsh web` 启动会打印 `dsh web: http://127.0.0.1:3080/?token=…`，桌面版翻遍日志和控制台都找不到这行。
- **根因**：launch token 每次进程启动随机生成，**只存在内存里**，经进程间通信交给 App 外壳——不落盘、不进任何日志、Local Storage 里也没有。前文「grep 日志抓 token」对桌面版完全无效。
- **解决**：从正在运行的 App 进程内存里把 `127.0.0.1:19387/?token=…` 字符串扫出来（只读扫描，不干扰运行，无需重启）。本机现成脚本：`python D:\myFiles\dsh\_scan-desktop-token.py`（自动找主进程，直接打印拼好的手机门链接）。
- **记住**：token 每次重启 App 都会变，旧链接作废。不过手机第一次用 token 链接打开后，服务器发给浏览器一个**持久签名 cookie**（绑定域名，默认 30 天，签名密钥是落盘的）——之后 App 重启一般不用重抓；哪天再遇 401 就重跑脚本。

### 坑 10：围栏没有 `--trusted-host` 注入口——页面能开、聊天记录出不来

- **现象**：手机开 `https://<域名>:19387`，token 能进、页面正常，但聊天记录/接口全部 403——就是前文坑 3 的桌面变体。
- **根因**：桌面宿主启动参数写死为 `--no-open --port 19387`，围栏白名单是空的；带 `Origin` 的 API 全被拒。curl 验证发现不了（curl 不发 Origin）。
- **解决**：改桌面 profile 的**补丁层** `~/.dsh/profiles/desktop/cordis.patch.yml`（用户目录下的文件，App 升级不丢），文件末尾追加：

  ```yaml
  - id: connection
    name: "@deepseek-ai/dsh-client-connection"
    config:
      trustedHosts:
        - <MagicDNS域名>
  ```

  域名**不带端口**（匹配任意端口）；这行的 config 只有这一个键，照抄即可。改完**重启桌面 App** 生效。
- **原理一句话**：围栏只查两件事——「Host 在白名单或是回环」+「Origin 等于 Host」。浏览器同源请求天然满足第二条，所以白名单补上域名就够了。

### 坑 11：补丁里写 `!!js` 表达式会让 token 抖动（303/401 交替）

- **现象**：按 bundle 官方注释的部署示例写成 `trustedHosts: !!js "['域名', ...拼接…]"` 后，同一个 token 一会儿 303 一会儿 401，同一秒内复测结果都不同。
- **根因**：`!!js` 表达式在 profile 补丁层会让 connection 插件**反复重载**，每次重载 launch token 跟着轮换——等于门锁在不停换钥匙。
- **解决**：**写静态数组**（坑 10 的写法）。桌面宿主本来就不传 `--trusted-host` 旗子，静态写法没有任何损失。

### 桌面版生命周期两条

- **桌面 App 一关，手机链接就死**（网关 502）：它不是独立常驻服务，手机要用时电脑上 App 得开着。这是它和 `dsh web` / 3083 那种独立实例的本质区别。
- 围栏边界与前文一致：`/api/host.*`（选文件夹、打开路径等）是本机专属接口，手机上永远 403——设计如此，这类操作回电脑上做。
